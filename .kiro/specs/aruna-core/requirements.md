# Requirements Document — Aruna Core

**Project:** Aruna Core — one AI agent skeleton for small businesses, proven by two applications
**Competition:** Kiroween 2026 (Devpost) · Category: **Skeleton Crew** · Bonus claimed: Best Startup Project
**Status:** DRAFT v1 — 18 Nov 2026 — awaiting founder review (Gate 1)
**Build window:** all code for this project is written between 30 Oct and 4 Dec 2026, spec-first in Kiro.

---

## Introduction

Aruna is an AI agent platform for small business owners, built by PahamAI (Indonesia). The owner runs daily operations — checking stock, following up suppliers, handling bookings, chasing invoices — semi-manually, and loses money to missed checks, wrong inputs, and forgotten follow-ups.

This project builds **Aruna Core**: a lean, reusable skeleton (tenant configuration, owner workspace, an assistant named by the owner, a task pipeline with verification and approval gates, an append-only audit log, and a daily briefing) that becomes a working application for a specific business purely by loading that business's **playbook**: its catalog, hours, thresholds, and message templates.

The skeleton is proven by two real applications from PahamAI's own pipeline, sharing the same codebase:

1. **Denana** — a women-only facial treatment studio in Bima (services: treatment catalog + bookings).
2. **Toko Seragam** — a school-uniform retail shop specialising in scout (pramuka) uniforms (retail: product variants + stock + supplier purchase orders).

Product decisions carried over from the Aruna blueprint v3 (9 Oct 2026, founder-locked): business-first; the assistant's name is customizable (default "Aruna"); the owner may talk to the assistant or directly to a specialist agent; one app — external channels are connectors, never the experience; mobile-first for the owner; tenant data separation and data export are mandatory from day one.

## Project constraints

- **C1 — Fresh build.** The repository, its `/.kiro` directory, and all application code are created inside the competition window. The pre-existing Aruna blueprint and the separate WhatsApp Follow-up Agent (an n8n product) are design inputs only; no code is copied from them and they are not part of this submission.
- **C2 — Thin slice.** This document defines the whole competition scope. Anything not listed under Requirements is out of scope (see "Explicitly out of scope") and belongs to the post-competition roadmap.
- **C3 — Safety mandate.** The AI model never has authority to mark a payment as paid or settled, and never executes a refund. Payment-adjacent states change only through deterministic rules plus explicit owner approval.
- **C4 — Real tenants, honest data.** Both proof applications use the real businesses' shapes (catalog types, hours, workflows). Personal data of real customers is never used; demo data is synthetic.

## Glossary

- **Tenant** — one business running on Aruna Core (e.g., Denana). All tenant data is strictly partitioned.
- **Playbook** — the per-business configuration that turns the skeleton into an application: business profile, catalog, opening hours, thresholds, templates, and which vertical pack is active.
- **Maestro** — the orchestrating assistant the owner talks to. Its display name is configurable per tenant; the default is "Aruna".
- **Specialist Agent** — a scoped agent (e.g., Stock, Booking) the owner can also address directly.
- **Task** — a unit of agent work moving through the pipeline: Queued → Working → In Review → Pending Approval → Done (or Rejected/Expired).
- **Checker** — the verification step (deterministic rules first, model review second) that every agent output passes before it can reach the owner or an external party.
- **Approval Gate** — the point where an action that writes externally or touches money waits for the owner's explicit decision.
- **Audit Log** — the append-only record of every agent action, check result, approval, and outcome.
- **Briefing** — the scheduled per-tenant summary (morning priorities + previous-day recap) generated by the skeleton's routine engine.
- **Vertical Pack** — the small set of domain entities and flows a business type adds on top of the skeleton (Services Pack: treatments + bookings; Retail Pack: variants + stock + purchase orders).

## Requirements

### Requirement 1 — Tenant foundation and data separation

**User story:** As a platform operator, I want every business's data strictly partitioned per tenant, so that one tenant can never see or affect another tenant's data.

#### Acceptance Criteria

1. THE SYSTEM SHALL attach a tenant identifier to every business record it stores (catalog items, tasks, bookings, stock, purchase orders, audit entries).
2. WHEN a user or agent requests data, THE SYSTEM SHALL return only records belonging to that user's tenant.
3. IF a request references a record of a different tenant, THEN THE SYSTEM SHALL refuse it and record the attempt in the Audit Log.
4. WHEN a tenant is offboarded, THE SYSTEM SHALL produce a complete export of that tenant's data (structured files: JSON or CSV) before any deletion occurs.
5. THE SYSTEM SHALL support at least two concurrently active tenants with different vertical packs on the same deployment.

### Requirement 2 — Playbook configuration (the skeleton switch)

**User story:** As a platform operator, I want a business to become a working application by configuration alone, so that onboarding a new tenant never requires new core code.

#### Acceptance Criteria

1. THE SYSTEM SHALL load a Playbook containing: business name and type, opening hours, catalog, thresholds (e.g., low-stock limit, approval amount limit), message templates, active vertical pack, and the assistant's display name.
2. WHEN only the Playbook changes (same codebase), THE SYSTEM SHALL present the corresponding business's application: its catalog, its flows, its assistant name, and its briefing content.
3. IF a Playbook field required by the active vertical pack is missing, THEN THE SYSTEM SHALL refuse to activate that tenant and report exactly which fields are missing.
4. THE SYSTEM SHALL ship with two complete Playbooks: Denana (Services Pack) and Toko Seragam (Retail Pack).

### Requirement 3 — Owner workspace (mobile-first)

**User story:** As a business owner who works from my phone, I want one workspace where I can see everything my agents are doing, so that I stay in control without doing the data entry myself.

#### Acceptance Criteria

1. THE SYSTEM SHALL present a task board with the pipeline columns Queued, Working, In Review, Pending Approval, and Done.
2. WHILE the viewport is phone-sized, THE SYSTEM SHALL present the board as a per-status stacked view with filters, and every critical action (approve, reject, chat, view briefing) SHALL be completable from that viewport.
3. WHEN a task changes status, THE SYSTEM SHALL show the responsible agent, the task's origin (routine, Maestro, or direct command), and its check and approval history on the task card.
4. THE SYSTEM SHALL provide one navigation shell shared by both proof applications; only Playbook-driven content differs.

### Requirement 4 — Talking to the assistant and to agents

**User story:** As an owner, I want to ask the assistant for the big picture or command a specialist agent directly, so that I can work the way Symphony-style workspaces allow — one system, any entry point.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide one chat thread with the Maestro and one thread per active Specialist Agent.
2. WHEN the owner issues a command in any thread, THE SYSTEM SHALL create or update a Task in the workspace and record the command in the Audit Log, regardless of which thread received it.
3. WHEN the owner asks the Maestro what an agent is currently doing, THE SYSTEM SHALL answer from the live task and audit data, not from generated text alone.
4. THE SYSTEM SHALL display the assistant name from the Playbook (default "Aruna") consistently in chat, briefings, and the workspace.
5. WHEN the owner renames the assistant in settings, THE SYSTEM SHALL use the new name everywhere from that moment on, without code changes.

### Requirement 5 — Checker and approval gates

**User story:** As an owner, I want every agent output verified before it reaches me, and nothing external or money-related to happen without my explicit approval, so that an agent's mistake can never silently cost me money or reputation.

#### Acceptance Criteria

1. WHEN a Specialist Agent produces an output intended for the owner or an external party, THE SYSTEM SHALL route it through the Checker before it becomes visible as actionable.
2. THE Checker SHALL apply deterministic checks first (required fields present, numbers consistent with source records, recipient matches the source record) and SHALL flag any inconsistency as an anomaly on the Task instead of passing it through.
3. WHEN an action would send a message externally, create a supplier commitment, or touch payment state, THE SYSTEM SHALL place the Task in Pending Approval and SHALL NOT execute the action before the owner approves it.
4. IF an approval is not decided within the configured expiry (default 15 minutes), THEN THE SYSTEM SHALL cancel the action and mark the Task Expired.
5. THE SYSTEM SHALL NOT change any payment state (paid, settled, refunded) on a model's say-so; such changes SHALL occur only via deterministic rules plus explicit owner approval (constraint C3).
6. WHEN the owner approves or rejects, THE SYSTEM SHALL record the decision, the decider, and the timestamp in the Audit Log.

### Requirement 6 — Audit log

**User story:** As an owner, I want a permanent, tamper-evident record of everything my agents did, so that any error can be traced to its exact step.

#### Acceptance Criteria

1. THE SYSTEM SHALL append an entry to the Audit Log for every agent action, Checker result, approval decision, and data export.
2. THE SYSTEM SHALL NOT provide any function that edits or deletes Audit Log entries.
3. WHEN the owner opens a Task, THE SYSTEM SHALL show the Audit Log entries belonging to that Task in chronological order.

### Requirement 7 — Services Pack (proof application 1: Denana)

**User story:** As the owner of a facial studio, I want booking requests captured, verified, and confirmed only with my approval, and a morning view of today's bookings, so that no appointment is ever double-booked or forgotten.

#### Acceptance Criteria

1. THE SYSTEM SHALL hold a treatment catalog for Denana (treatment name, duration, price) loaded from its Playbook.
2. WHEN a booking request arrives through the in-app intake (customer name, treatment, requested date and time), THE SYSTEM SHALL create a Task containing a draft confirmation prepared by the Booking agent.
3. THE SYSTEM SHALL check the requested slot against existing confirmed bookings and SHALL flag an overlap as an anomaly before the Task can reach Pending Approval.
4. WHEN the owner approves the confirmation, THE SYSTEM SHALL record the booking as confirmed; WHEN the owner rejects it, THE SYSTEM SHALL record the rejection and its reason.
5. THE SYSTEM SHALL include today's confirmed bookings and pending booking requests in Denana's morning Briefing.

### Requirement 8 — Retail Pack (proof application 2: Toko Seragam)

**User story:** As the owner of a uniform shop, I want stock checked automatically, low stock flagged, and supplier follow-ups drafted for my approval, so that I never discover an empty shelf from a customer.

#### Acceptance Criteria

1. THE SYSTEM SHALL hold a product catalog with variants (item, size) and a stock count per variant, loaded from the Playbook and editable by the owner.
2. WHEN the stock routine runs, THE SYSTEM SHALL flag every variant at or below the Playbook's low-stock threshold in a Stock Task.
3. WHEN the owner commands a supplier follow-up for a flagged item or a stale purchase order, THE SYSTEM SHALL draft the follow-up message from the Playbook template, with the item, quantity, and purchase-order reference taken from the records.
4. THE SYSTEM SHALL route the draft through the Checker and the Approval Gate before marking it sendable (Requirement 5); in this slice, "sending" is recorded in-app — no live external channel is connected (see Out of Scope).
5. WHEN the owner records a goods receipt against a purchase order, THE SYSTEM SHALL update stock by the received quantity and SHALL flag any difference from the ordered quantity as an anomaly for the owner.

### Requirement 9 — Daily briefing (shared routine)

**User story:** As an owner, I want one briefing that tells me yesterday's results and today's priorities, so that I start the day informed without opening five different tools.

#### Acceptance Criteria

1. THE SYSTEM SHALL generate a Briefing per tenant on the Playbook's schedule, from that tenant's real records (tasks, bookings, stock flags, pending approvals).
2. THE Briefing SHALL list pending approvals explicitly, so nothing awaiting the owner is buried.
3. WHILE the two proof tenants use different vertical packs, THE SYSTEM SHALL generate both Briefings from the same routine code, with content differing only through Playbook data.
4. THE SYSTEM SHALL archive Briefings so the owner can reopen any past Briefing from the workspace.

### Requirement 10 — Model gateway

**User story:** As a platform operator, I want all model calls behind one provider-agnostic gateway, so that the brain can be swapped per tenant without touching agent code.

#### Acceptance Criteria

1. THE SYSTEM SHALL route every model call through a single gateway interface; agent code SHALL NOT call a provider SDK directly.
2. THE SYSTEM SHALL allow the provider and model to be configured per tenant (environment or settings), with a sensible default.
3. THE SYSTEM SHALL record model usage (calls and tokens, when the provider reports them) per tenant and per Task in the Audit Log.
4. IF the configured provider is unreachable, THEN THE SYSTEM SHALL fail the Task with a visible error state — never with a fabricated result.

### Requirement 11 — Demo and evaluation readiness

**User story:** As a judge (or any evaluator), I want to run and try both applications myself, so that I can verify the skeleton claim instead of taking the pitch's word for it.

#### Acceptance Criteria

1. THE SYSTEM SHALL run from a fresh clone using only the setup steps documented in the repository README.
2. THE SYSTEM SHALL provide seed data that activates both proof tenants with realistic catalogs and a small history of tasks and briefings.
3. THE SYSTEM SHALL be reachable as a live deployed web application, usable on a phone viewport, with any test credentials documented in the submission (not in the public repository).

## Explicitly out of scope (post-competition roadmap)

- Live external channel connectors (WhatsApp Business API, Instagram, email sending). The existing WhatsApp Follow-up Agent remains a separate product; this slice records outbound actions in-app.
- Payment execution and payment-gateway integration (agents prepare; humans execute).
- Offline-first synchronisation (addressed at design level only in this slice).
- Voice interaction and voice name-mention (blueprint Fase 1.5).
- Social-media management for tenants.
- Multi-business accounts (one owner running several tenants) and a self-serve tenant signup.
- A full BYO-API-key settings UI (the gateway is configurable; the polished settings screen is roadmap).
- Generative image features for tenant branding (Aruna v2 roadmap).

## Open items for the design phase (Gate 2)

1. Hosting and data stack confirmation (blueprint default: Next.js PWA + Supabase Postgres on Vercel free tiers).
2. Authentication approach for owner accounts in the slice (single owner per tenant).
3. How the in-app intake for Denana bookings is presented to evaluators (public intake page vs. simulated request button).
4. Build account decision (founder decision, required before repo creation): Kiro Pro+ under the PahamAI AWS account, or the founder's personal Kiro account holding the 4,000 Kiroween credits that expire 31 Dec 2026.
